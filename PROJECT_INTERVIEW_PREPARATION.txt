SECTION 1 - PROJECT OVERVIEW
============================================================

1. WHAT THE PROJECT DOES:
   This project is a multi-role enterprise e-commerce platform that allows customers to 
   browse products, manage shopping carts and wishlists, place orders with real-time 
   inventory reservation, and make secure payments via Razorpay. It also provides a 
   granular admin control system where internal staff members are assigned specific 
   business roles (e.g., Product Manager, Order Manager, Inventory Manager) to manage 
   the platform.

2. PROBLEM IT SOLVES:
   Traditional simple e-commerce implementations suffer from critical flaws:
   * Race conditions during checkout when multiple customers purchase the same stock item simultaneously.
   * Vulnerability to price/address tampering after checkout.
   * Rigid permissions where staff members have all-or-nothing admin access.
   * Weak payment flows that trust client-side success reports without cryptographic verification.
   This project solves all four problems using database row-level locking (`select_for_update`), 
   atomic transaction boundaries (`@transaction.atomic`), historical JSON address snapshots, 
   dynamic DRF permission mapping based on Django Groups, and server-side HMAC SHA256 
   signature verification.

3. TARGET USERS:
   * Online Shoppers (Customers) who create accounts, save addresses, build carts, and purchase items.
   * Super Administrators who assign roles and permissions to staff members.
   * Product Managers who handle categories, brands, products, attributes, and variants.
   * Order & Inventory Managers who oversee order fulfillment, stock levels, and inventory adjustments.

4. MAIN MODULES:
   * `apps.accounts`  : Custom User model, Address book, JWT Auth, RBAC permissions, Staff role management.
   * `apps.catalog`   : Multi-level Categories, Brands, Attributes, AttributeValues, Products, Images, ProductVariants.
   * `apps.inventory` : Stock quantities, Reserved quantities, Low-stock alerts, Inventory transaction logs.
   * `apps.cart`      : Persistent User Cart, Cart Items with variant selections, Wishlist management.
   * `apps.orders`    : Atomic Order creation service, Order Items snapshot, Order status history log.
   * `apps.payments`  : Razorpay session creation, Cryptographic payment verification, Refund tracking.
   * `apps.reviews`   : Ratings and customer review system (Extended catalog feature).
   * `apps.marketing` : Promotional coupons and discount rules (Extended catalog feature).

5. MAIN FEATURES:
   * Email-based User Auth & JWT Token Blacklisting.
   * Granular RBAC (`IsSuperAdmin` and `HasModelPermission`).
   * Dynamic Product Variant pricing and attribute mapping (Size, Color, Storage).
   * Concurrency-safe checkout with row locking (`select_for_update`).
   * Immutable Address Snapshots stored directly inside JSON fields in Order objects.
   * Razorpay API integration with HMAC-SHA256 signature verification.

6. IMPORTANT WORKFLOWS:
   * Registration -> Login (Receive JWT Access & Refresh Tokens) -> Store Tokens in Client.
   * Browse Catalog -> Select Product Variant -> Add to Cart -> Adjust Quantities.
   * Initiate Checkout -> Select Shipping/Billing Address -> Execute Atomic Service (`create_order_from_cart`).
   * Lock Inventory Rows -> Reserve Stock -> Generate Order -> Clear Cart.
   * Initiate Razorpay Payment (`create_payment_order`) -> Convert Amount to Paise -> Return Razorpay Order ID.
   * Execute Frontend Razorpay Popup -> Receive Signature -> Post to Verification Endpoint (`verify_payment`).
   * Verify HMAC Signature -> Mark Payment PAID -> Mark Order CONFIRMED.

7. TECHNOLOGY STACK OVERVIEW:
   * Backend: Python 3.12+, Django 5.x, Django REST Framework 3.15+, `djangorestframework-simplejwt`, `razorpay` SDK.
   * Database: PostgreSQL / SQLite3 managed via Django ORM.
   * Authentication: JSON Web Tokens (JWT) with refresh token blacklisting stored in `token_blacklist` tables.
   * Frontend Integration: React with Axios HTTP client, JWT authorization header injection, React Router v6.

8. ARCHITECTURE OVERVIEW:
   Layered Monolithic Architecture with a decoupled API layer. Requests hit DRF ViewSets / APIViews, 
   which check authentication and dynamic permission classes (`HasModelPermission`). Business logic 
   is isolated in dedicated service layers (`apps.orders.services`, `apps.payments.services`) wrapped 
   inside `@transaction.atomic` database transactions.

[5-MINUTE IN-DEPTH ARCHITECTURAL WALKTHROUGH]
"Let me walk you through the end-to-end architecture and implementation details of my e-commerce platform.

1. System Architecture & Domain Design:
   I designed the backend following clean architectural principles by decoupling HTTP/API handling from 
   business logic. Views in `apps.orders.views` and `apps.payments.views` handle request parsing and 
   validation, while complex business flows are executed inside service modules like `services.py`. 

2. Security & RBAC:
   Security is enforced strictly on the backend. Authentication relies on Simple JWT tokens. To implement 
   Role-Based Access Control without hardcoding permissions for every view, I built a custom permission 
   class named `HasModelPermission`. It inspects the incoming request method—mapping GET to `view`, 
   POST to `add`, PUT/PATCH to `change`, and DELETE to `delete`—and combines this with the view queryset's 
   model name to evaluate `user.has_perm('app_label.action_modelname')`. Superadmins can assign staff members 
   to roles like Product Manager or Order Manager using custom role management APIs (`/api/v1/auth/admin/users/{id}/assign-role/`).

3. Data Integrity & Inventory Locking:
   One of the biggest engineering challenges in e-commerce is handling flash sales or high-concurrency checkouts. 
   If two requests hit the backend at the exact same millisecond for an item with 1 remaining stock, a standard 
   query will suffer from a race condition. I solved this by wrapping the checkout process in `@transaction.atomic` 
   and using `select_for_update()` on the `Inventory` table for the specific variant IDs in the cart. This forces 
   the database to place an exclusive row lock. The second request must wait until the first transaction completes, 
   ensuring stock is never over-allocated. Furthermore, I decoupled available stock from reserved stock using 
   properties on the `Inventory` model (`quantity - reserved_quantity`).

4. Address Snapshotting:
   If a user updates their home address in their profile next month, historical invoice records for orders placed 
   today must not change. To guarantee immutability, during checkout I serialize the current `Address` model instance 
   into a flat JSON snapshot (`shipping_address` JSONField on the `Order` model).

5. Payment Gateway Verification Flow:
   For payments, I integrated Razorpay. When a user requests payment initialization, the backend calculates the order 
   total, converts it to INR paise (e.g., 500.00 INR becomes 50000), and requests a `razorpay_order_id` from the Razorpay API. 
   When the client completes payment on the frontend modal, Razorpay returns a `razorpay_payment_id` and a `razorpay_signature`. 
   The client posts these credentials to `/api/v1/payments/verify/`. The backend uses `razorpay.Client.utility.verify_payment_signature` 
   to compute an HMAC-SHA256 signature using our server-side secret key. Only if the signatures match is the payment marked 
   as `SUCCESS` and the order status updated to `CONFIRMED` within an atomic transaction.

6. Database Query Optimizations:
   To prevent N+1 query problems across nested REST endpoints (such as retrieving products with their brands, categories, 
   images, and variants), I heavily utilized Django ORM optimizations like `select_related('category', 'brand')` and 
   `prefetch_related('images', 'variants')` inside ViewSet querysets. This reduced the database queries per request 
   from dozens down to 2 or 3 queries."

ARCHITECTURAL INTERVIEW QUESTIONS & ANSWERS
------------------------------------------------------------

Q1: Why did you choose a service-oriented layer in Django instead of putting all business logic inside Serializers or Views?
SHORT INTERVIEW ANSWER:
"I separated complex business logic into a dedicated service layer (`services.py`) to keep Views thin, single-responsibility, and reusable. Serializers should handle data validation and formatting, while Views handle HTTP requests and status codes. Multi-model transactional logic—like locking inventory, creating orders, snapshotting addresses, and generating audit logs—belongs in a service layer where it can be wrapped in `@transaction.atomic` and tested independently."

DEEP TECHNICAL ANSWER:
"Placing complex workflows inside DRF ViewSets or Serializers leads to fat controllers and tightly coupled code that is difficult to unit test without mocking HTTP requests. For example, order checkout (`create_order_from_cart`) touches 6 different models: `Cart`, `CartItem`, `Inventory`, `Order`, `OrderItem`, and `OrderStatusHistory`. Putting this in `Serializer.create()` obscures validation responsibilities and makes background task integration (e.g., Celery) difficult. By isolating this logic in `apps.orders.services`, I can call `create_order_from_cart` from a REST view, a CLI management command, an asynchronous queue, or a test runner cleanly."

Q2: How does the system handle database concurrency during high-volume flash sales?
SHORT INTERVIEW ANSWER:
"We handle concurrency using database row-level locking with Django's `select_for_update()` inside atomic transactions. When a checkout starts, the service queries and locks the specific inventory rows for the items in the user's cart. Other concurrent transactions attempting to read/lock those same inventory rows must wait until the current transaction completes, preventing race conditions and over-allocation of stock."

DEEP TECHNICAL ANSWER:
"In high-concurrency environments, naive checks like `if inventory.quantity >= requested_qty:` suffer from race conditions (Time-of-Check to Time-of-Use bugs). Two simultaneous requests read quantity = 1, both pass validation, and both write back stock, resulting in negative stock. In `apps.orders.services`, I implemented:
`Inventory.objects.select_for_update().filter(variant_id__in=variant_ids)`
This emits a `SELECT ... FOR UPDATE` SQL query in PostgreSQL. The database engine acquires an exclusive lock on those specific inventory rows. If User B attempts to checkout the same variant simultaneously, User B's database query blocks until User A's transaction either commits or rolls back. Stock availability is calculated using `available_quantity = quantity - reserved_quantity`, ensuring 100% data consistency."

INTERVIEW QUESTIONS:
Q1: Why did you create a custom User model instead of using Django's default User?
ANSWER: Django's default User model uses `username` as the primary identifier. Modern e-commerce platforms require authentication via `email`. Extending `AbstractUser` at project start allowed set `email` as unique, add fields like `phone`, `profile_image`, `is_customer`, and avoid costly database migration refactoring later.

FOLLOW-UP: What happens if you try to change to a custom User model after running migrations in a Django project?
ANSWER: Changing `AUTH_USER_MODEL` midway through a project breaks existing foreign key relationships across migration history. It requires wiping migrations and the database or performing complex custom SQL migration surgery. That is why creating a custom user model upfront is a Django best practice.


FEATURE 2: DYNAMIC ROLE-BASED ACCESS CONTROL (RBAC)
* WHAT IT DOES: Restricts administrative APIs to specific staff roles (Product Manager, Order Manager, Inventory Manager, Super Admin).
* IMPLEMENTATION: Built custom `HasModelPermission(BasePermission)` which inspects `view.queryset.model` and maps HTTP methods (`GET` -> `view`, `POST` -> `add`, `PUT` -> `change`, `DELETE` -> `delete`) to dynamically call `request.user.has_perm(permission_name)`. Super Admins assign users to Django `Group`s via `/api/v1/auth/admin/users/{id}/assign-role/`.
* IMPORTANT FILES:
  - `backend/apps/accounts/permissions.py`
  - `backend/apps/accounts/views.py`
  - `backend/apps/accounts/serializers.py`

INTERVIEW QUESTIONS:
Q2: How does `HasModelPermission` dynamically check permissions without hardcoding them in views?
ANSWER: `HasModelPermission` extracts the model class directly from `view.queryset.model`. It maps the incoming HTTP method to Django's standard permission prefixes (`view`, `add`, `change`, `delete`). It formats the string `app_label.action_modelname` (e.g., `catalog.add_brand`) and checks if the user possesses that permission directly or via Django Group membership.

FOLLOW-UP: What happens if a view does not define a `queryset` attribute?
ANSWER: If a view does not define `queryset` (such as a generic `APIView`), accessing `view.queryset.model` raises an `AttributeError`. To handle such views, we must either override `get_queryset()`, explicitly set `queryset` on the view, or pass specific permission classes like `IsSuperAdmin` or `IsAuthenticated`.


FEATURE 3: PRODUCT CATALOG & VARIANTS ARCHITECTURE
* WHAT IT DOES: Manages multi-level categories with self-referencing parents, brands with auto-slug generation, products, product gallery images, attributes (Color, Size), attribute values (Red, XL), and product variants with distinct SKUs and prices.
* IMPLEMENTATION: `Category` uses `models.ForeignKey("self", on_delete=models.PROTECT)`. `Brand` and `Category` auto-slugify in `save()`. `ProductVariant` links to `Product` via ForeignKey and `AttributeValue` via `ManyToManyField`.
* IMPORTANT FILES:
  - `backend/apps/catalog/models.py`
  - `backend/apps/catalog/views.py`
  - `backend/apps/catalog/serializers.py`

INTERVIEW QUESTIONS:
Q3: Why is `Category` set to `on_delete=models.PROTECT` on its parent relationship?
ANSWER: `models.PROTECT` prevents a parent category (e.g., "Electronics") from being deleted if child categories (e.g., "Laptops", "Smartphones") or products are attached to it. Attempting to delete it raises Django's `ProtectedError`, ensuring catalog hierarchy and data integrity.

FOLLOW-UP: How do you prevent N+1 query overhead when fetching a list of products with their images and variants?
ANSWER: In `ProductViewSet`, I configured `queryset` with `select_related("category", "brand")` to perform SQL `JOIN`s for single-valued relationships, and `prefetch_related("images", "variants")` to fetch multi-valued relations in bulk queries, reducing DB operations from N+1 down to 3 queries regardless of item count.


FEATURE 4: ATOMIC CHECKOUT & INVENTORY RESERVATION SERVICE
* WHAT IT DOES: Validates user cart items, locks inventory rows, verifies stock, calculates order pricing, snapshots shipping address, creates order items, reserves stock, and clears cart.
* IMPLEMENTATION: Service function `create_order_from_cart` in `apps.orders.services` decorated with `@transaction.atomic` using `select_for_update()`.
* IMPORTANT FILES:
  - `backend/apps/orders/services.py`
  - `backend/apps/orders/views.py`
  - `backend/apps/inventory/models.py`

INTERVIEW QUESTIONS:
Q4: Explain line-by-line what happens when two users checkout the last stock unit of a variant at the exact same time.
ANSWER: User A and User B submit requests simultaneously. Both enter `create_order_from_cart` inside atomic transactions. The line `Inventory.objects.select_for_update().filter(...)` executes SQL `SELECT ... FOR UPDATE`. The database grants the lock to User A first. User B's DB query pauses on the locked row. User A's transaction checks stock (`quantity - reserved_quantity >= 1`), succeeds, creates order, increments `reserved_quantity`, and commits. Lock releases. User B's query unblocks, reads updated `reserved_quantity`, checks stock (`available_quantity == 0`), raises `ValidationError("Only 0 units available")`, and rolls back. Overbooking is mathematically impossible.

FOLLOW-UP: Why do you store `reserved_quantity` separately from `quantity` in the Inventory model?
ANSWER: Keeping `quantity` (total physical stock in warehouse) separate from `reserved_quantity` (stock held for pending/unpaid orders) allows clear stock visibility. When an order is shipped, `quantity` is decremented and `reserved_quantity` is decremented. If an unpaid order is cancelled, we simply decrement `reserved_quantity` without altering physical inventory logs.


FEATURE 5: RAZORPAY PAYMENT & HMAC SIGNATURE VERIFICATION
* WHAT IT DOES: Creates Razorpay payment orders in paise, launches frontend payment modal, and cryptographically verifies server-side signature before updating order to PAID.
* IMPLEMENTATION: `create_payment_order` converts amount (`int(Decimal(total_amount) * 100)`). `verify_payment` executes `client.utility.verify_payment_signature(...)`.
* IMPORTANT FILES:
  - `backend/apps/payments/services.py`
  - `backend/apps/payments/views.py`
  - `backend/apps/payments/models.py`

INTERVIEW QUESTIONS:
Q5: Why do we convert `order.total_amount` to an integer multiplied by 100 before calling Razorpay?
ANSWER: Financial payment gateways like Razorpay require order amounts in the smallest currency sub-unit to avoid floating-point arithmetic errors. In Indian Rupees (INR), the smallest sub-unit is paise (1 INR = 100 paise). Passing floating-point numbers like `499.99` in JSON leads to rounding errors. Converting `Decimal("499.99") * 100` yields integer `49999`.

FOLLOW-UP: Why can't we trust the frontend success callback when Razorpay completes payment on the client side?
ANSWER: Client-side JavaScript execution can be intercepted, modified, or forged by a malicious user using browser console or tools like Postman. A attacker could mock a success response without paying. Server-side HMAC-SHA256 verification uses our secret key (`RAZORPAY_KEY_SECRET`) to verify the signature generated by Razorpay. If the payload was tampered with, signature verification fails and payment is rejected.

Q1: What is the difference between `APIView`, `GenericAPIView`, `ListCreateAPIView`, and `ModelViewSet` in DRF, and where did you use each in this project?
ANSWER: 
* `APIView`: Base class providing basic HTTP method handlers (`get`, `post`, `put`, `delete`). Used in `RegisterView`, `LogoutView`, `CheckoutView`, `ChangePasswordView` for custom procedural logic.
* `GenericAPIView`: Extends `APIView` with standard helper methods (`get_queryset`, `get_serializer`).
* `ListCreateAPIView` / `RetrieveUpdateDestroyAPIView`: Concrete view helpers for listing/creating and retrieving/updating/deleting. Used in `AddressListCreateView` and `AddressDetailView`.
* `ModelViewSet`: Combines list, create, retrieve, update, and destroy actions into a single class driven by routers. Used in `CategoryViewSet`, `BrandViewSet`, `ProductViewSet` for clean RESTful CRUD.

Q2: How does `select_related` differ from `prefetch_related` in Django ORM?
ANSWER:
* `select_related`: Works by creating an SQL `JOIN` query and bringing back fields of the related object in the single database query. Works on single-valued relationships: `ForeignKey` and `OneToOneField`. (Used in `ProductViewSet` for `category` and `brand`).
* `prefetch_related`: Performs a separate SQL query for each relationship and does the joining in Python. Works on multi-valued relationships: `ManyToManyField` and reverse `ForeignKey`. (Used in `ProductViewSet` for `images` and `variants`).

Q3: How are status codes used across backend responses?
ANSWER:
* `200 OK`: Successful retrieval or action completion (e.g., login success, profile update).
* `201 Created`: Successful creation of a resource (e.g., user registration, order checkout).
* `400 Bad Request`: Validation failures (e.g., insufficient stock, invalid refresh token, incorrect password).
* `401 Unauthorized`: Unauthenticated request (missing or invalid JWT access token).
* `403 Forbidden`: Authenticated user lacks RBAC permission (`HasModelPermission` or `IsSuperAdmin` rejection).
* `404 Not Found`: Resource does not exist (e.g., invalid address ID during checkout).

Q4: What is the benefit of defining `related_name` on ForeignKeys throughout your models?
ANSWER: `related_name` specifies the reverse relation attribute on the target model. For example, `related_name="orders"` on `Order.user` lets us access a user's orders via `user.orders.all()` instead of `user.order_set.all()`. It makes ORM queries more readable and avoids attribute name collisions in prefetching.

Q5: Where is input data validation enforced in the backend architecture?
ANSWER: Validation occurs at three distinct layers:
1. Serializer Field Types & Validators (`EmailField`, `UniqueConstraint`, custom `validate()` methods).
2. Service Layer Checks (business rule validations like checking `variant.is_active` and `available_quantity` in `services.py`).
3. Database Model Constraints (`unique=True`, `UniqueConstraint(fields=['cart', 'variant'])` in PostgreSQL/SQLite).

Q1: How does Axios handle JWT access and refresh token management?
ANSWER: Axios uses Request and Response Interceptors.

Q2: How are protected routes implemented in React Router?

If authenticated, it renders the child components; if unauthenticated, it redirects the user to `/login` with `state: { from: location }` to allow post-login redirection.

If the backend returns HTTP 400 (e.g. "Only 2 units available"), the client reverts local state to the actual server quantity and displays a notification toast.

SECTION 9 - AUTHENTICATION & AUTHORIZATION
============================================================

1. LOGIN & JWT FLOW:
   * Client POSTs email & password to `/api/v1/auth/token/`.
   * Django verifies password against stored PBKDF2 hash.
   * `Simple JWT` generates Access Token (payload: user_id, exp, token_type='access') and Refresh Token (payload: user_id, exp, jti, token_type='refresh').
   * Client stores Access Token in memory/state and Refresh Token in HttpOnly cookie or secure storage.
   * Subsequent API calls attach `Authorization: Bearer <access_token>`.

2. LOGOUT & TOKEN BLACKLISTING:
   * Client POSTs refresh token to `/api/v1/auth/logout/`.
   * `LogoutView` validates token and calls `token.blacklist()`.
   * `Simple JWT` inserts the token's unique identifier (`jti`) into the `token_blacklist_blacklistedtoken` database table.
   * If an attacker attempts to reuse that refresh token at `/api/v1/auth/token/refresh/`, Simple JWT queries the blacklist table, rejects the request with HTTP 400 "Token is blacklisted", and blocks token renewal.

3. RBAC INTEGRATION (`HasModelPermission`):
   * Inspects `request.user`. If user is `is_superuser`, grants access immediately (`return True`).
   * Extracts model from `view.queryset.model`.
   * Maps request HTTP method:
     - `GET`    -> `"view"`
     - `POST`   -> `"add"`
     - `PUT`/`PATCH` -> `"change"`
     - `DELETE` -> `"delete"`
   * Constructs permission string: `f"{model._meta.app_label}.{action}_{model._meta.model_name}"` (e.g. `catalog.add_category`).
   * Evaluates `request.user.has_perm(permission_name)`. If user belongs to a Group ("Product Manager") that holds `catalog.add_category`, request is authorized.

SECTION 10 - SECURITY QUESTIONS
============================================================

Q1: How are passwords stored securely in the database?
ANSWER: Django hashes passwords using PBKDF2 with a SHA256 hash algorithm and a unique per-user salt. Passwords are never stored in plain text.

Q2: How does the backend prevent SQL Injection attacks?
ANSWER: All database interactions are routed through Django ORM's parameterized queries. Input values passed to `.filter()`, `.get()`, or `.create()` are properly escaped by the database driver, eliminating SQL injection risks.

Q3: How is server-side payment verification secured against tampering?
ANSWER: When Razorpay returns payment identifiers (`razorpay_order_id`, `razorpay_payment_id`, `razorpay_signature`), `verify_payment` calculates an HMAC-SHA256 hash of `order_id + "|" + payment_id` using our secret `RAZORPAY_KEY_SECRET`. If the calculated hash does not match `razorpay_signature` character-for-character, the request is rejected as tampered.

Q4: [POTENTIAL WEAKNESS] What happens if CORS is misconfigured in production settings?
ANSWER: [POTENTIAL WEAKNESS] If `CORS_ALLOW_ALL_ORIGINS = True` is left enabled in production, malicious third-party websites can make authenticated API requests on behalf of users if tokens are stored insecurely.
HOW TO IMPROVE IT: Restrict `CORS_ALLOWED_ORIGINS` strictly to our trusted frontend domains (e.g. `https://shop.example.com`).

Q5: [POTENTIAL WEAKNESS] Are JWT access tokens revokable before expiration?
ANSWER: [POTENTIAL WEAKNESS] Standard JWT access tokens are stateless and validated via cryptographic signature without DB lookup. If an access token is leaked, it remains valid until its 15-minute expiration.
HOW TO IMPROVE IT: Keep access token lifetime short (e.g., 5-10 minutes) and use Redis token revocation lists for high-security environments.

SECTION 14 - "WHY DID YOU DO THIS?" QUESTIONS
============================================================

QUESTION 1: Why did you implement a separate `services.py` module for checkout instead of using `Serializer.create()`?
ANSWER: Ordering is a multi-domain workflow involving carts, inventory locking, address snapshotting, order creation, item breakdown, and status logging. DRF Serializers are designed for single-entity validation and transformation. Packing 150 lines of multi-model transactional orchestration inside `OrderSerializer.create()` violates Single Responsibility Principle and hinders reusability.

ALTERNATIVE: Writing all creation logic inside `OrderSerializer.create()`.
WHY NOT THE ALTERNATIVE: Serializer unit testing requires constructing complex nested JSON request contexts; calling checkout logic from CLI or webhooks becomes clunky.
TRADEOFF: Introducing `services.py` adds an extra architectural layer, but significantly improves maintainability and testability.

QUESTION 2: Why did you choose JWT authentication with token blacklisting over traditional Django session cookies?
ANSWER: Single Page Applications (React) built as decoupled frontends operate cleaner when using stateless authorization headers (`Bearer <token>`). Session cookies require managing CSRF tokens and sharing domain cookie policies across subdomains. JWT blacklisting bridges the gap between stateless tokens and immediate revokability upon logout.

ALTERNATIVE: Django session cookies (`django.contrib.sessions`).
WHY NOT THE ALTERNATIVE: Harder to scale across cross-origin single-page applications and mobile app clients.
TRADEOFF: Database lookup required on logout to record blacklisted tokens.
